# AGENTS.md

Инструкции обязательны для любого AI-агента, работающего с Foodler.
Вложенные `backend/AGENTS.md` и `mobile/AGENTS.md` уточняют правила своей части.

## Перед изменением

1. Прочитать корневой README и только релевантный scoped `AGENTS.md`.
2. Проверить `git status`; пользовательские изменения не перезаписывать.
3. Найти существующий поток данных, тип или компонент через `rg`.
4. Для API сначала менять FastAPI/Pydantic, затем выполнять `make contract`.

## Документация и Git workflow

Перед каждым коммитом агент обязан проверить все относящиеся к задаче README,
CHANGELOG, guides, `docs/`, `.env.example`, ADR, known issues, legal-тексты и
API-контракт. Нужные документы обновляются **до** создания коммита; если
обновление не требуется, причина указывается в сообщении коммита и итоговом
отчёте.

После выполнения задачи и успешных релевантных проверок AI-агент самостоятельно:

1. создаёт ветку `agent/<краткое-название>` от актуальной базовой ветки;
2. добавляет только файлы текущей задачи;
3. создаёт один содержательный conventional-style commit;
4. отправляет ветку в `origin` через `git push -u origin <ветка>`;
5. сообщает имя ветки, SHA коммита, статус push и результаты проверок.

Нельзя коммитить или push в `main`, включать чужие незакоммиченные изменения,
перезаписывать историю или обходить ошибки авторизации/сети. Если branch, commit
или push невозможен, агент фиксирует точную причину и оставляет изменения
нетронутыми для пользователя.

## Границы

- Не хранить секреты, реальные токены, пароли и персональные данные в коде,
  fixtures, логах, документации или generated-файлах.
- Не редактировать `contracts/openapi.json` и `mobile/src/api/generated/`
  вручную.
- Не дублировать DTO между backend и mobile. Для Foodler API использовать
  generated OpenAPI-типы.
- Не добавлять `any`, `@ts-ignore`, отключение линтера, `noqa`, skip/xfail или
  широкие `except Exception` без локального обоснования.
- Не смешивать функциональное изменение, массовое форматирование и
  архитектурный рефакторинг в одной задаче.
- Не менять публичный API, SQLite-схему или SQLAlchemy-модель без миграции,
  обратной совместимости и теста.
- Сохранять local-first/offline поведение mobile. Серверная ошибка не должна
  скрывать уже сохранённые локальные данные.
- Не логировать JWT, refresh-токены, QR payload, чеки, email или AI-контекст.

## Качество реализации

- Сначала переиспользовать существующую абстракцию; повторение логики в третьем
  месте требует выделения общей функции/компонента.
- Состояние интерфейса должно иметь явные loading, empty, success и error
  состояния. После локальной записи UI обновляется без повторного входа на экран.
- Сетевые операции имеют timeout, типизированную ошибку и предсказуемый retry.
- Backend использует структурированный `logging`, а не `print`.
- Новое поведение покрывается тестом на наблюдаемый результат, а не детали
  реализации.

## Definition of done

1. Выполнены релевантные тесты.
2. Выполнен `make check`; при изменении контракта перед ним — `make contract`.
3. Любое изменение кода обязательно сопровождается проверкой и обновлением
   связанных `README.md`, `CHANGELOG.md`, guides, `docs/`, `.env.example`,
   ADR/known issues и публичного API-контракта. Если конкретный документ менять
   не требуется, агент обязан явно подтвердить это в итоговом сообщении.
4. Документация описывает только фактически реализованное поведение; нельзя
   оставлять старые endpoint-ы, поля ответа, провайдеров или гарантии.
5. В итоговом сообщении перечислены изменения, проверки, обновлённые документы
   и оставшиеся риски, а также ветка, SHA коммита и статус push.
