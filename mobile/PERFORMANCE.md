# Производительность mobile

## Бюджеты

Проверка выполняется в release-сборке на Android-устройстве среднего класса:

- p95 UI- и JS-кадра при прокрутке списка из 500 чеков — не более 16,7 мс;
- пропущенных кадров в сценарии прокрутки — не более 1%;
- реакция на нажатие — не более 100 мс;
- локально сохранённый или удалённый чек появляется/исчезает на открытом
  экране не позднее 100 мс без ожидания сети;
- первый полезный экран после готовности SQLite — не позднее 2 секунд.

Это release-бюджеты, а не гарантия для development-сборки с Metro.

## Обязательный сценарий перед релизом

1. Собрать release-вариант: `npm run android -- --variant release`.
2. Подготовить локальную базу с 500 чеками и не менее 20 позиций в каждом.
3. В Android Studio Profiler записать cold start, десятисекундную прокрутку
   списка, открытие большого чека, добавление и удаление ручного чека.
4. Проверить бюджеты выше и приложить trace/сводку к release-задаче.
5. При регрессии сначала проверить render-time allocation, JS `onScroll`,
   невиртуализированные списки и анимации без native driver.

## Реализованные ограничения

- `ReceiptsScreen` и `ReceiptDetailScreen` используют `FlatList` с bounded
  render window.
- Строка списка memoized и не создаёт `Animated.Value` во время render.
- SQLite mutations публикуются одним observable-сигналом; серверный batch
  схлопывается в одно перечитывание экрана.
- График временного ряда агрегирует каждый чек один раз вместо повторного
  полного прохода для каждого календарного периода.
- Неиспользуемые JS `onScroll` удалены; progress кредитов использует native
  transform.
